# 从个人使用出发理解 Harness

记录日期：2026-10-16。性质：基于课程的概念解释及个人讨论结论；下列实施方案仍待实际验证。

具体操作方法以 [knowledge/ 方法库](../knowledge/README.md) 为主；本页保留个人讨论背景和选择，不作为第二份方法维护入口。

## 先分清两组概念

| 划分 | 含义 | 在个人使用 Codex 时的对应 |
| --- | --- | --- |
| 内部 Harness | Agent 产品内置的执行机制 | 推理、调用工具、观察结果、继续执行等运行机制 |
| 外部 Harness | 围绕具体任务组织的规则、资料、工具、环境和状态 | 项目指令、Skill、检查脚本、参考资料、运行条件、任务记录 |
| 外层循环 | 管理整个任务的计划、阶段、进度和调整 | 先整理目录，再提炼知识，最后做图；按阶段检查是否继续 |
| 内层循环 | 改善当前一步的执行质量 | 提供要求、执行、检查结果，再据此修正 |

两组划分不是同一维度。外部 Harness 可以同时组织外层和内层循环。也不能简单认定 AGENTS.md 是外层、Skill 是内层：规则和 Skill 都可能描述不同规模的工作过程。

课程框架见 [双层循环与四个子系统](../KNOWLEDGE.md#section-01)。

## 当前个人使用的建议

先打磨内层循环：每次任务明确做什么、怎样检查、出错后怎样调整。复杂任务再补充外层阶段和检查点。任务层次与 Agent 数量没有一一对应关系，一个会话也能管理多个阶段。

| 场景 | 建议重点 | 需要的检查 |
| --- | --- | --- |
| 总结一篇文章 | 内层 | 覆盖主要观点，区分原文与解释，检查来源 |
| 整理会议纪要 | 内层 | 决定、待办和责任人是否有依据；缺失内容明确标记 |
| 修改一个范围明确的小问题 | 内层 | 针对行为做适当验证，核对改动范围 |
| 排查未知原因的问题 | 轻量外层加内层 | 收集事实、提出假设、逐项验证，避免直接猜改 |
| 跨模块功能开发 | 外层加内层 | 阶段依赖、方案、实现、验证、Review；每步独立验收 |
| 持续整理课程 | 外层加内层 | 外层跟踪范围与进度，内层核对每项知识的准确性 |

“先内层、再按需增加外层”是针对当前个人使用的建议，不是所有工作的固定优先级。

## 外部 Harness 可以落在哪些地方

| 组成 | 常见载体 | 应当放什么 |
| --- | --- | --- |
| 指令 | 当前任务要求、项目 AGENTS.md | 目标、边界、完成标准、稳定约定 |
| 工具与技能 | Skill、终端命令、脚本、MCP | 重复的方法、具体动作、可执行检查 |
| 环境 | 依赖、配置、工作目录、权限 | 工具运行条件和执行边界 |
| 状态 | 计划、检查点、决策与交接文件 | 进度、关键结论、验证证据、下一步 |

当前仓库自身就是一个轻量的外部 Harness：README 提供入口，AGENTS.md 提供协作要求，知识文件提供资料，状态文件支持接续，检查脚本提供结构反馈。

读取这些文件不会自动改变 Codex 全局配置，也不会把本仓库规则安装到其他项目。具体产品行为以官方文档与当前版本为准。

## 用前馈痴迷做一次小改进

课程来源：[第 12 讲](https://time.geekbang.org/column/article/1016080)，结合 [第 10 讲](https://time.geekbang.org/column/article/1014410) 与 [第 13 讲](https://time.geekbang.org/column/article/1016964)。

### 问题现象

结果不满意时，不断追加“更准确、更完整、注意细节”，却没有建立执行后的检查。这里展示的是可尝试的改法，并非判定用户已经存在该问题。

### 从哪里直接使用

用 [把要求转成检查](../knowledge/03-feedback-and-quality.md#feedback-first) 设计本轮改进，结合 [完成证据](../knowledge/03-feedback-and-quality.md#completion-evidence) 和 [分级反馈](../knowledge/03-feedback-and-quality.md#graded-feedback) 验收。步骤、例外及可复制提示词均在对应方法中。

按 [一次小实验](../knowledge/06-environment-and-improvement.md#improvement) 比较是否减少遗漏与返工，结果记录到 [实践模板](../templates/experiment.md)。当前尚无实际对比结果；是否固化到其他项目的规则或全局配置，需要明确目标和授权范围。

## 需要保留的边界

- 模型自检属于推断，能用工具核实的内容应尽量获取实际结果。
- 换一个 Agent 验收不自动保证独立；共享错误标准时仍可能共同漏检。
- 提示词是指导；重要权限与批准应由执行边界落实。
- 环境锁定只能固定可控部分，不能保证外部服务和模型行为永远不变。
- 本仓库的学习状态不是用户能力测评；有疑问时通过一个小任务验证理解。
