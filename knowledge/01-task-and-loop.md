# 把任务变成可执行的工作

一项任务先明确目标和终点，再安排执行。规模较小时，用“指导、执行、检查、调整”完成；规模较大时，再增加阶段、依赖和进度管理。

## 先分清两组概念

内部 Harness 是产品内置的 Agent 运行机制；外部 Harness 是我们围绕工作配置的要求、知识、工具、环境和记录。内外层循环则是工作过程的划分：外层安排整体进度，内层把当前一步做好。

因此，我们在外部 Harness 中既能写阶段安排，也能配置当前步骤的检查。一个会话可以承担两层循环，一个 Skill 也可能包含不同规模的流程。是否增加 Agent，要另看独立收益和协调成本。

## 方法一  先写任务卡

**适用现象：** 结果看着完整，却总不是自己想要的；每轮都要补充之前没有说明的关键条件。

先写出以下内容，未知处保留为待确认，不让 Agent 偷偷补成事实。

| 项目 | 要回答什么 |
| --- | --- |
| 目标 | 这次工作要解决哪个具体问题，给谁使用 |
| 输入 | 使用哪些材料，哪些已经确认，哪些可能过时 |
| 范围与约束 | 允许做到哪里，必须保留什么，有哪些实现限制 |
| 交付物 | 最后要文件、方案、分析结论，还是实际修改 |
| 完成条件 | 看见什么证据，才认为目标已满足 |
| 边界与例外 | 输入缺失、来源冲突、无法执行时怎样处理 |

**怎样做：** 让 Agent 先复述任务卡；只核对会影响结果的歧义，再执行。已明确的信息不反复追问，能通过现有资料核实的内容先查。

**辅助示例：** “整理会议纪要”可以具体为：依据本次记录，输出决定、待办、责任人和未决问题；没有提到责任人的事项标为待确认；不得替参会者编造承诺。检查时逐项回看原记录，而不是只看排版是否漂亮。

**怎样验收：** 随机拿一个输入缺失或冲突的情况，看任务卡是否给出了处理方式；再检查交付物与完成条件能否一一对应。

```text
先把我的请求整理成任务卡：目标、输入、范围与约束、交付物、完成条件、边界情况。标出会改变结果的假设，能从现有材料确认的先核实。其余关键问题再向我确认，然后在已授权范围内执行。
```

<a id="choose-loop"></a>
## 方法二  按任务规模选择循环

**先用一个内层循环：** 输入范围清楚、产物能够一次验收、执行过程不需要多个相互依赖的阶段。例如整理一段记录、检查一份文档、修改范围明确的问题。

把过程写成四件事：开始前读什么和遵守什么；现在做什么；做完看什么；未通过时修什么、补什么或报告什么。

**增加外层循环：** 需要多个可验收产物，前一步影响后一步，执行中要调整计划，或工作会跨会话接续。例如持续整理课程、完成跨模块功能、排查原因未知的问题。

外层只保留必要信息：阶段、阶段产物、进入下一步的条件、当前进度。每个阶段里面仍然使用内层循环；不能把“阶段完成”建立在 Agent 自报完成上。

**辅助示例：** 课程知识整理分为确认资料范围、提炼知识、检查准确性、形成应用方法。每一阶段有自己的检查；发现缺课时返回范围核对，不直接继续美化文档。

**不必拆分的情况：** 单一步骤已经有足够上下文，继续切碎只会增加交接。多 Agent 也不是复杂任务的默认前提。

```text
先判断这个任务能否在一个内层循环内独立验收。若需要多个相互依赖的阶段，列出每阶段产物、验证办法和当前进度；否则保持简单。不要仅为套用框架增加阶段或 Agent。
```

## 方法三  决定哪部分交给工具

能明确计算的数量、字段、格式等交给可执行检查；需要理解含义、推断影响和判断质量的部分由模型分析，重要取舍由人确认。工具成功只能证明它检查到的条件成立。

例如，清单有 20 项可以计数；这 20 项是否覆盖主题还需内容判断。两者一起使用，才接近任务的完成条件。

## 使用边界

任务卡是协作约定，不自动改变权限。方法要应用到其他项目时，先明确项目与授权范围，并读取目标项目的规则。目标变化后，先更新完成条件，不能一边沿用旧验收，一边追求新结果。
