# 让完成有证据让修正有方向

每次交付前，依据原始目标检查实际结果；没有满足时，决定继续修正、补充输入还是交给人处理。只增加事前要求，无法替代这个过程。

<a id="feedback-first"></a>
## 方法一  把要求转成检查

**适用现象：** 已经强调过很多次的要求，仍然每次都要由人指出遗漏。

按“要求 → 观察对象 → 检查动作 → 不通过时的处理”改写。

| 事前要求 | 做完怎样检查 | 未通过怎样处理 |
| --- | --- | --- |
| 内容准确 | 核对关键结论与依据是否一致 | 修正或标记尚未核实 |
| 不遗漏 | 将目标清单与实际结果逐项对照 | 补齐遗漏或明确无法完成的部分 |
| 表达清楚 | 用读者需要回答的问题检查内容 | 补充缺失解释，删除干扰内容 |
| 遵守范围 | 检查实际修改或处理了哪些对象 | 撤回无关部分或报告范围变更 |

先约定完成后如何判断，再补充有助于首次做对的指导。检查不一定要写脚本；能机械判断的用工具，需要语义理解的给出清楚标准。

**验收：** 对一份故意含有明显问题的样例执行检查，看是否能发现该问题。检查提示词写得漂亮，不代表检查真正有效。

```text
先把本任务的重要要求转成检查项，分别说明观察对象和检查办法。完成后执行这些检查，发现问题先修正；无法检查的内容说明原因，不用自报“已完成”代替验证。
```

<a id="completion-evidence"></a>
## 方法二  根据原始范围独立验收

**适用现象：** 只处理了容易部分，却对全部任务宣布完成。

先保存待处理范围，再记录实际处理结果，最后从原始范围核对覆盖。批量任务可以用“每项都有成功、失败或未处理状态”检查遗漏；开放任务则用目标问题和质量标准核对。

验证者应能看到原始要求及原始结果，不能只看执行者写的漂亮总结。机械部分交给脚本；重要语义判断可采用单独检查或人工审阅。即使换 Agent，也需要检查双方是否沿用了同样的错误假设。

**辅助示例：** 输入 12 条工作记录，检查是否每条都有去向；数量全部对应之后，再检查是否误解、重复合并或编造事实。数量正确只是覆盖证据的一部分。

**交付至少说明：** 做了什么；检查了什么及结果；哪些未检查、为什么；遗留事项是否影响使用。

<a id="graded-feedback"></a>
## 方法三  分级处理问题并设置结束条件

**适用现象：** 不停修一个问题又破坏另一个问题，始终不知道什么程度可以结束。

| 等级 | 处理方式 | 举例 |
| --- | --- | --- |
| 必须满足 | 未满足就修复，或明确报告无法完成 | 关键事实有错误，主要需求未实现 |
| 需要报告 | 给出影响与评估，由人决定是否继续投入 | 已覆盖要点但篇幅略短 |
| 可选改善 | 不阻塞交付，按需处理 | 不影响理解的轻微表达偏好 |

级别按任务目标确定，不按工具名称固定。修正时先处理必须满足的问题，减少常规成功信息对失败信号的干扰。

**停止条件：** 必须满足项通过且已报告其余事项时，可以结束；缺少必要输入、超出授权或同一问题重复修正没有新进展时，说明阻塞点与下一步需要的证据，不无限重试。具体时间和重试预算可随任务事先约定。

```text
按本任务目标区分必须满足、需要报告和可选改善。先处理必须满足项；每次修正后核对是否破坏已通过的重要条件。缺少输入或反复没有进展时说明原因与下一步，不为满足所有偏好无限返工。
```

<a id="human-judgment"></a>
## 方法四  把人的判断放在合适位置

自动检查依照给定标准运行，人仍要判断目标与标准是否合适。应按动作性质选择介入方式，而非所有动作统一批准或统一放行。

| 情况 | 可考虑的介入方式 |
| --- | --- |
| 需求正在形成，需要不断做取舍 | 人持续参与关键判断 |
| 某个动作会对外产生后果 | 动作前批准 |
| 可以先形成可撤回的草稿，再决定落地 | 提交前批准 |
| 常规工作明确，部分情况无法按现有规则判断 | 异常升级 |
| 范围有界、影响较小且可纠正的重复任务 | 授权范围内自主执行，事后抽查 |

评估可逆性、外部影响、涉及价值和适用要求，也考虑累计影响。高频、信息不充分的批准容易变成机械点击，应让每次介入都提供具体内容与影响。

**执行边界：** 重要批准应由工具权限或统一执行入口落实，不能仅依赖提示词。模型自报“很有把握”不等于正确概率，不能未经校准就据此自动放行。

## 一次完整的小循环

要求摘要覆盖指定主题 → 生成摘要 → 对照主题和来源检查 → 补齐、修正或标明缺失 → 通过关键条件后交付。这个循环已经可以直接用于一次日常任务，无需先建立复杂系统。
