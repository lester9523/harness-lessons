# 把有效经验变成可复用方法

先通过实际任务找出有效做法，再把其中稳定的部分保存。复用的重点是过程、检查与转向清楚，输出内容可以随输入变化。

<a id="solidify"></a>
## 方法一  为经验选择合适载体

**适用现象：** 同一类任务每次从头解释，前一次纠正无法改善下一次执行。

先区分本次临时处理与可复用经验，再决定放在哪里。

| 内容 | 适合的载体 | 不适合混进去的内容 |
| --- | --- | --- |
| 长期有效的目标边界和原则 | 简短规则与决策记录 | 当前任务的零散进度 |
| 某类任务的指导、执行、检查与调整 | 方法文档或 Skill | 只有一次有效且原因未明的结论 |
| 确定性的计算与机械操作 | 脚本或工具 | 无法明确定义的主观质量判断 |
| 本次进度、证据、下一步 | 状态与交接记录 | 无范围限制的永久规则 |
| 临时猜测和中间产物 | 临时区与待验证记录 | 冒充事实的长期结论 |

**操作顺序：** 做一次 → 解释为什么有效 → 换一个相近输入检查 → 明确适用范围 → 保存稳定部分 → 持续复查。尚无足够证据时可以保存为候选方法，不包装成已验证经验。

不必一开始就安装 Skill。普通文档也能承载方法；当任务确实反复发生，再考虑封装。

<a id="skill-design"></a>
## 方法二  把重复任务写成完整技能

**适用现象：** 已有稳定的方法，但每次触发、执行顺序和完成条件都不一致。

定义六项：何时使用和不使用；需要哪些输入；事前指导；具体行动；检查标准；失败后的调整、停止和交付。需要跨阶段协作时，再说明接收什么状态、返回什么结果。

自由度按任务特点确定：机械、容易明确检查的步骤可以固定；需要分析和表达的步骤保留判断空间。不能因为想稳定，就逐字规定所有动作，也不能只有方向而没有完成条件。

**拆分依据：** 子任务是否有独立的使用场景，能否自己形成完整循环。只是挪走一段操作说明，不一定值得变成另一个 Skill。

**验收：** 用正常输入、缺失输入和不适用任务分别检查：是否正确触发、能否发现输入不足、会不会越界执行。平台字段与加载机制需按实际工具核对，不从方法说明直接推断配置语法。

```text
把这次有效做法整理为候选技能，说明触发与不适用条件、输入、指导、行动、检查、调整与交付。区分必须固定和可由模型判断的部分。先给出正常、缺失输入和不适用三种验证情形；不要直接安装到全局配置。
```

<a id="anchors"></a>
## 方法三  用示例减少歧义

想稳定复现某类产物时，分别检查四个维度，而不是只说“参考这个样子”。

| 维度 | 给出什么 | 检查什么 |
| --- | --- | --- |
| 输出 | 空模板和完成示例 | 必要内容是否齐全，是否满足任务用途 |
| 风格 | 合适与不合适的表达样例 | 语气与读者是否匹配，事实是否仍准确 |
| 流程 | 步骤、分支和每步条件 | 必需步骤是否发生，例外是否走对分支 |
| 结构 | 内容组织方式与边界 | 信息是否放对位置，有无跨越职责 |

**辅助示例：** 会议纪要模板定义“决定、待办、未决问题”；完成示例展示如何将模糊记录写成可核对的内容；检查负责发现无依据的责任人。只有模板，可能格式齐全但内容失真。

```text
结合这份模板与示例，说明要复用的结构和质量标准。保留与本次任务相关的模式，不复制示例里的事实。生成后按标准检查，不以“看起来相似”作为唯一验收。
```

## 方法四  阻止旧模式继续扩散

**适用现象：** 已经要求改用新方法，Agent 仍从大量旧产物中复制不再推荐的做法。

给出明确的正向范例及入口；将能检查的约束落实为检查；识别现有问题形成存量基线，要求新工作不继续增加；在相关工作触及时逐步清理。

范例负责给方向，检查负责守边界。基线不是豁免所有旧问题；高影响问题仍需优先处理。规范一旦变化，范例和检查要一起更新。
