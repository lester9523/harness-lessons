# 让执行可复现让改进有依据

Agent 的结果同时受输入、规则、工具、环境和模型影响。出问题时先保留证据、比较变化；找到有效方法后，再更新自己的知识。

<a id="environment"></a>
## 方法一  对比环境而非盲改提示词

**适用现象：** 同样的工作昨天能做，今天失败；或家里能执行，到公司换电脑后失效。

先记录失败时的输入、执行步骤、工具结果和环境条件，再与上一次成功运行比较。

| 层次 | 需要知道什么 | 可采取的措施 |
| --- | --- | --- |
| 工作区 | 当前目录、文件版本、输入是否相同 | 确认仓库版本，核对未提交改动 |
| 运行环境 | 运行时、依赖、配置和必要权限 | 明确初始化步骤，固定可控版本 |
| 技能与工具 | 实际版本、是否被替换、接口是否一致 | 按需局部化并记录版本 |
| 外部服务 | 返回内容、契约、访问条件是否变化 | 增加适配层，保留失败信号与回归检查 |
| 模型 | 使用的模型及可见配置是否变化 | 记录可获取的信息，对关键任务做回归对比 |

先固定本机可控条件，再处理分发和隔离。适配层能吸收部分接口变化，但不能保证外部服务永远不变；封装成镜像也不能冻结模型输出。

**验收：** 在声明的条件下重新执行，判断故障是否复现或消失，并保留实际证据。不要承诺自然语言输出逐字相同。

```text
先保存当前失败证据，对比输入、工作区、依赖、配置、工具、外部服务与模型的变化。提出最小的验证动作，逐项缩小原因。没有新证据前，不要同时修改提示词、依赖和业务规则。
```

<a id="improvement"></a>
## 方法二  用一次小实验检验改进

**适用现象：** 学了很多方法，却不知道哪一种真的适合自己；每次同时改很多东西，效果无法解释。

1. 选择一个反复发生、能够观察结果的问题。
2. 写出原因假设，例如“关键要求只有事前强调，没有事后检查”。
3. 尽量保持任务和材料相近，本轮只调整一个主要环节。
4. 事先确定检查办法，例如遗漏项、无依据结论、返工与人工核对成本。
5. 记录实际结果，包括没有改善或无法执行。
6. 说明限制与其他可能因素，再决定是否采用、继续验证或放弃。

使用 [实践记录模板](../templates/experiment.md)。过程完成不等于方法有效；一次变好也不等于已证明普遍有效。先积累足够接近自己工作场景的证据。

## 方法三  将变化更新回知识库

实践产生的新认识先判断属于哪一类：

- 新事实：记录来源、时间和适用范围。
- 用户偏好或决定：确认来源和场景，保留理由。
- 方法调整：写清旧做法、新做法、变化原因和验证情况。
- 尚未解释的结果：保留为假设或未决事项。

可直接使用的方法维护在对应 `knowledge/` 文件；来源变化更新课程索引和课程整理；实际结果放在实践记录。入口和提示词只引用方法，不复制整套操作步骤。

内容更新不必等待知识体系“完美”。先修正当前证据支持的部分，同时标出尚不确定的部分。具体维护流程见 [UPDATING.md](../UPDATING.md)。

## 六个原则怎样落到日常动作

| 原则 | 我们在工作中做什么 |
| --- | --- |
| 双层循环 | 小任务先跑完整内层；复杂任务再管理阶段与进度 |
| 仓库即规范 | 为结论确定主要载体，并持续维护来源和入口 |
| 渐进式信息披露 | 先读索引，根据当前任务展开必要细节 |
| 计算与推断分离 | 机械条件用工具核实，语义质量另做判断 |
| 最小干预 | 重复检查尽量自动化，人保留方向、取舍和重要动作的判断 |
| 可复现性优先 | 保存足够的输入、版本、步骤和证据，使变化能够追查 |
